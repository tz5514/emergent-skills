Emergent skills：一套讓 AI agent 做出好工程的生產線

The most common failure mode in software development is misalignment.

軟體開發最常見的失敗模式是不對齊。

—— Matt Pocock，mattpocock/skills README

序

為什麼需要這套東西

你下一個 prompt，agent 跑了五分鐘、改了七個檔、開好 PR、宣稱完工。code 能跑、test 也綠——但打開 diff 細讀，總有地方不對勁：

  • 能跑但結構糟——跨 module 的邏輯硬塞進一個 50 行的 function
  • 悄悄走捷徑——edge case 過不了，就改 test 讓它跟著實作走
  • 完成 9/10 就宣稱做完——漏掉的那件往往最基本
  • 用話術遮蓋偷工——「這個 trade-off 是合理的，先 ship 再 iterate」

單看都是小事，累積起來是 AI coding agent 時代特有的失敗模式：表面像完工，codebase 的長期健康在悄悄退化。這不是 AI 寫不出 code 的問題，是 AI 不知道什麼叫好工程的問題。

Emergent skills 就是為此存在：八個 skill 組成一條從想法到上線的生產線——把計畫拷問清楚、寫成規格、審查規格、拆成票、一票一票實作驗證，最後把架構決定沉澱成文件。每個流程有明確的進出品，每個流程都預設 agent 會漂移，用機制而不是叮嚀來守。

淵源

Emergent skills 蓋在 Matt Pocock 的 mattpocock/skills 之上——不是「參考了它的想法」，是強依賴的上層封裝，抽掉官方 skills 就跑不起來：

  • emergent-to-spec／emergent-to-tickets 在 runtime 直讀官方 to-spec／to-tickets 的完整本文當 baseline 流程，官方沒裝在旁邊就整場停
  • emergent-implement 每次執行都正式載入官方 codebase-design 與 tdd 當實作方法，收尾用 code-review 自審
  • emergent-implement-tickets 的整合審查直接借用 code-review 的 Spec axis 定義

分工很清楚：官方 skills 負責 baseline 流程與實作方法，emergent skills 往上疊五層官方沒有的東西——

  1. 工程哲學的明文化（emergent-design）
  2. 拷問對齊的機制化（emergent-grill）——官方的 grill-with-docs 已經會邊追問邊更新文件；這裡把「問」跟「寫」兩頭都機制化。問的一頭：每個問題先過濾——你答得出或 code 裡查得到的不拿去煩使用者、architecture-level 的必問、一次只問一題；提問內建三招技巧（磨利模糊詞、用具體情境逼出概念邊界、對 code 交叉查證）；想收尾前必須先列「若只能再問三題」的清單，由使用者喊停才算問完。寫的一頭：明確拍板才歸檔、CONTEXT.md 詞條展示原文確認才寫入、ADR 過獨立審查才落草稿
  3. spec 的自動雙軸審查迴圈（emergent-spec-review）
  4. ADR 的完整生命週期機制（emergent-adr）
  5. 無人值守的 ticket orchestration（emergent-implement-tickets）

對官方那套設計的深入分析，見我們先前的研究報告；本文哲學章的精華即取材於它。

第一章

Emergent design：整套 skills 的姓氏

這套 skills 裡的每一個都以 emergent- 開頭，這不是裝飾。整套系統的每個設計決定，都從同一個哲學推出來——emergent design（湧現設計）。這章把這個哲學講清楚，因為不懂它，後面每個流程的規矩看起來都像多餘的儀式；懂了它，你會發現每條規矩都在補同一個洞。

這章的內容有三層出身，先給全景，免得讀的時候分不清哪些是底、哪些是我們疊的：

第三層・我們疊的emergent skills 的明文化與延伸——把哲學寫成可正式載入的權威（sayability 分層、human-decision boundary、載體責任），以及本章的延伸分析
第二層・基石Matt 的翻譯——把 30 年的工程紀律物質化成 agent 讀得懂的 skills，並在 agent 時代押注 emergent design

一場 30 年的老戰場工程文化

「設計該在動手前想清楚，還是在動手的過程裡長出來」是一場打了至少 30 年、至今沒有共識的工程哲學辯論[1][2]。兩派的根本分歧長這樣[3]：

Spec-driven（規格驅動）Emergent design（湧現設計）
核心信念先思考完整、再實作設計透過實作浮現
流程設計階段做完所有重要決定，產出詳細規格；實作照規格執行先做最簡單能 work 的版本，從實作經驗累積設計理解，逐漸 refactor
失敗原因診斷規格不夠詳細或不夠正確預先設計時資訊不足、做了錯誤決定
根本假設思考夠久就能想清楚思考有極限，必須動手才能學到

先拆第一個常見誤解：emergent design 不是「不要規格」。要做什麼（產品行為、領域邊界）它一樣得先想清楚；它不預先定的只是「怎麼做」那一層：內部結構怎麼切、抽象放哪、function 怎麼設計，那部分留給實作中浮現。

第二個誤解：emergent design 也不是「比較隨興」。恰恰相反，它比 spec-driven 更依賴紀律[3]：正因為你不在前面把設計定死，你需要一整套機制確保「邊做邊改」不會滑成「邊做邊爛」。

整套 skills 的哲學權威（emergent-design）把這件事講成兩個都要拒絕的失敗極端[4]：

完全的預先設計是防禦性的。它能拉高下限，卻壓低了實作時判斷力的上限，而且詳細計畫從真實 code 開始偏離的那一刻起就開始過期。無約束的即興——vibe coding——則失去可預測性、可理解性、可持續維護性。

Sayability 分層：為什麼有些設計必須等實作emergent skills

為什麼不能靠更聰明、想更久，把設計預先全部做完？答案碰到一個認識論的老問題。人的設計直覺裡沉著大量 tacit knowledge（默會知識）——Michael Polanyi 那句話講得最透：「we can know more than we can tell」[5]，我們能知道的，多於我們說得出來的。有些設計理解沒辦法預先言說、寫進文件，它只能在你的手碰到 code、撞到具體約束的那一刻才浮現。

emergent-design skill 把這件事叫做 layers of sayability（可言說性分層）：設計知識有一部分能在任何 code 存在之前就可靠地說出來；但更多部分要等實作證據——真實的 code、真實的 caller、真實的 test、真實的整合——存在之後才變得可說[6][7][8]。硬把不可說的部分逼著預先定案，產出的是「打扮成決定的猜測」，而猜測正是會過期的東西。放在 agent 身上更具體：預先定案等於叫 agent 先在腦中局部模擬一次實作，再把推測出來的做法釘死成規格——這一釘輸兩次：

✗ 硬把不可說的預先釘死
動手前，腦中模擬一次實作脈絡遠不如動手時完整
↓
把推測出來的做法釘死成規格
↓
實作撞到真實約束✗ 輸第一次：預判錯了
↓
不能轉向，繞著錯的規格硬蓋✗ 輸第二次：手段被釘死，無法隨機應變
✓ 只定可說的，其餘留給浮現
動手前只定行為、邊界、契約這些在 code 存在前就可靠地可說
↓
實作：真 code、真 caller、真 test
↓
撞到問題＝學到新資訊
↓
內部做法跟著證據調整對的設計長出來，行為始終守住

所以真正的分界不是「要不要先設計」，而是哪一類決定能預先做好、哪一類必須等實作才做得好。emergent-design 給了一條明確的 human-decision boundary：一個決定需不需要人先定，判準其實只有一句話：這個決定會不會創造一個「別人會依賴的承諾」。skill 列了五種情況，全是這句話的具體型：

  • 對外的契約：使用者、外部系統、或呼叫你 code 的人看得到、會依賴的行為。例：API 的回傳格式、錯誤碼。你之後改它，別人就壞掉，所以不能讓它在實作中飄。
  • 跨 ticket 的共享邊界：兩張票各自實作、最後要接起來的那個介面。例：A 票做匯出、B 票做通知，「匯出完成事件長什麼樣」兩票都會碰。不先講好，兩個互相看不見的實作者就會各做各的。
  • 不可協商的硬約束：產品、相容性、資安、法務這類沒有討論空間的規定。例：個資不能出境、必須相容舊版 client。實作者不能用「我覺得這樣更好」推翻它。
  • 你明確拍板的選擇：你說了算的事。你說用 PostgreSQL，實作就不會自己換成它覺得更合適的東西。
  • 測試從哪裡測：所謂 testing seam，指測試伸進系統觀察行為的位置。例：這個功能從 HTTP API 測、還是從 service 層測。這要先講好，TDD 才有地方下第一根樁；至於內部私有結構怎麼測，留給實作。

反過來說，不創造以上任何承諾的選擇（module 怎麼切、抽象放哪、命名、內部結構）留給 codebase、tests 與實作回饋去長。一句話版本：會被別人依賴的，先定；只有自己看得到的，留給浮現。

Agent 時代：同一個選擇，重量變了emergent skills

這場辯論打了三十年，但過去它是溫和的，因為人類身上有兩層保險——而 agent 兩層都沒有：

人類Agent
手感 就算嘴上選 spec-driven、照著 plan 走，寫 code 時大腦仍不自覺持續做設計判斷：plan 不對就調、看到更好的抽象就改[9] 只做 explicit 指示的事，叫它照 plan 走就照 plan 走；實證上，多輪對話一旦走錯就傾向回不來，表現平均掉 39%[10]
自覺 偷懶跳過紀律時「知道自己在偷懶」，那個明知會留著，累積成下次的修正 跳過步驟是當下真心覺得合理，不是明知故犯；事後承認也不會累積，context 一漂又重新覺得跳過合理

更陰險的是偏離的長相：agent 不會說「我想偷懶」，它會說「有鑑於這個 session 的 context 已經很長，我決定採取更精簡的做法」，把紀律的衰減包裝成資源效率的理性權衡，聽起來像判斷力；而模型的自我解釋會系統性地不忠於真實原因，是有實證的行為[11]。

所以同一個選擇、同一次紀律偏離，套在人類身上被兩層緩衝墊稀釋，套在 agent 身上是全額的，而且它自己察覺不到。這三個事實——沒有 tacit 安全網、紀律會隨 context 漂移、偏離會偽裝成判斷——是理解整套 emergent skills 設計的鑰匙。你會在後面反覆看到同一個 pattern：凡是重要的事，emergent skills 從不依賴 agent「記得」或「自律」，一律改成機制。權威文件載不到就整場停掉、審查報告用 script 機械驗證、TDD 的紅綠不聽論證、reviewer 被隔離到拿不到會污染判斷的資訊、每張票派全新的 sub-agent。這些不是不信任的儀式，是對這三個事實的工程回應。

工程控制系統：五道紀律工程文化emergent skills

Emergent design 靠什麼不退化成 vibe coding？靠一套工程控制系統。emergent-design skill 列了五道紀律，兩種角色：TDD 與 tracer bullet 驅動設計往前長，deep modules、ubiquitous language、ADR 守護浮現的過程不失控。五道都不是新發明，每一道背後都站著一本經典：

Deep modules：窄介面藏住大量功能守護

John Ousterhout 在《A Philosophy of Software Design》（2018）[12]給「好模組」的定義：deep module，讓大量功能透過一個簡單的介面被使用。同一個 cacheGet(key)，淺的版本只是從 dict 拿值；深的版本介面一模一樣，內部默默處理過期、淘汰、thread safety，caller 完全不用知道。emergent design 特別需要它，因為 emergent 的核心動作是反覆 refactor：介面越窄、藏得越深，改內部就越不會外溢到 caller，你才敢一直動。它是一道守護的牆。

Ubiquitous language：一套共用的領域詞彙守護

Eric Evans 在《Domain-Driven Design》（2003）[13]觀察到：軟體失敗常常不是技術不強，是對問題領域的理解不精確。「訂單」這個詞，在不同人嘴裡可能指著微妙不同的東西。解法是讓開發者跟領域專家共用一套詞彙，而且直接進到 code 命名。emergent 的設計會不斷冒出新概念，沒有一份共用詞彙把它們釘住，同詞異義很快讓浮現的設計漂移失準。它守護的是語義的一致。

Architecture Decision Records：凍結決策當下的脈絡守護

Michael Nygard 2011 年的觀察[14]：架構不是一次決定的，是無數小決定累積的，而每個決定的理由很快被遺忘，半年後沒人記得「為什麼這樣設計」。ADR 用一頁 markdown 把決定當下的脈絡凍結下來：選了什麼、當時為什麼、考慮過哪些替代。emergent 過程會做大量決定，理由最容易蒸發，ADR 守護的是決策脈絡不流失。但不是每個決定都值得寫，寫太多就成了沒人讀的文件墳場。值得寫的決定要同時滿足三個條件：

  • 難以回頭：改起來的代價無法輕易收斂
  • 沒脈絡會令人意外：不知情的維護者會誤把刻意的選擇當成該修的問題
  • 真實取捨的結果：不是顯然正確，而是在多個合理選項裡挑了一個

三個都中才寫，其餘留在 code 裡就好。

TDD：紅綠循環驅動守護

Kent Beck 在《Extreme Programming Explained》（1999）[15]推廣的三步循環：先寫一個會失敗的測試（red）、寫最少的 code 讓它通過（green）、在綠燈下整理結構（refactor）。每個小循環都是一次微型設計實驗，結構從實驗中累積，這正是「設計在實作中浮現」的引擎本身。同時，描述行為（而非實作）的測試是 refactor 的安全網：改完跑一遍，綠燈就代表行為沒被改壞。所以 TDD 是雙重身分：驅動浮現的引擎，也是守護演化的網。

Vertical slice / tracer bullet：先跑通、再加厚驅動

Hunt 與 Thomas 在《The Pragmatic Programmer》（1999）[16]提出曳光彈：先做一條薄到端到端能跑通的線（schema 最小、一個 endpoint、一顆按鈕），再逐層加厚。好處是提早撞出整合問題，而不是各層各自做完、最後接起來才發現對不上。它就是 emergent 的操作節奏：先跑通、從跑起來的東西學到真實約束、再據此演化。

這五道紀律長期被推崇卻難以普及，因為每一條都是「現在痛、以後爽」，跟人類的短期誘因對著幹。這裡藏著 agent 時代真正的轉機：agent 沒有人類這套短期誘因——它不會「懶得寫 ADR」、不會「覺得 refactor 浪費時間」。這些被人性拖累三十年的紀律，第一次有機會被穩定地、不打折地執行——前提是你得把它們寫成 agent 讀得懂的清楚指令，而且（回到上一節）還得架上一層不依賴 agent 自律的外部強制。這兩件事加起來，就是 emergent skills。

資訊的載體責任：長壽與一次性emergent skills

這套哲學裡最實用的一塊，是回答「每一種資訊該住在哪」。原則是 locality 與 single authority：給每個意義一個唯一權威的家，住在能把它彰顯出來的、最近的耐久載體裡。

長壽載體（long-lived carriers）維護 ground truth，各管各的領土：

  • Code 擁有具體實作，以及一切能透過結構、型別、命名、行為表達的實作意圖。code 能講清楚的，就不需要註解。
  • Tests 擁有 user story 要求的可觀察行為——它是行為的耐久紀錄，取代一份重複的長期 user-story 文件。
  • Interfaces 擁有 caller 契約：caller 正確使用一個 module 需要知道的一切。介面實體上也是 code，但它是切給不同讀者的責任區：實作對維護者說話，介面對 caller 說話——caller 不該需要讀實作才會用。
  • 局部註解只擁有 code 無法彰顯的局部意圖。
  • CONTEXT.md 擁有共享的領域語言。
  • ADR 只在「持久的決策脈絡、且以上載體都不適合承載」時才進入考慮——而且這樣的候選還得通過獨立的必要性審查。

一次性載體（one-shot carriers）是過境中的目標：spec 記錄所有已拍板的需求與設計、把它們遞交給實作者，是「已拍板的對話」進入「實作」的必經交接層；tickets 把 spec 的工作切成這一輪的單位。兩者都只描述目標與預定工作——不管實作前、實作中、實作後，就算 code 一時跟它們長得一樣，ground truth 永遠只住在長壽載體裡。

那「規格」到底住在哪？把上面的分工倒過來讀就是答案：行為的規格住在 tests、領域詞彙的規格住在 CONTEXT.md、架構決策的規格住在 ADR，而最底層「實作怎麼做」的規格沒有文件、也不需要文件：code 就是它唯一且永遠同步的紀錄。這就是「code-as-spec」：採用 emergent design，邏輯上必然走到「詳細實作規格只存在於 code 本身」。也因此，spec 寫完、tickets 做完之後，該留的知識都已經住進長壽載體，文件本身就功成身退；回頭維護它們，等於養一份注定漂移的第二真相。

觀察一個 pattern 五個流程裡，除了 emergent-spec-review（它是被 emergent-to-spec 呼叫的審查引擎）之外的四個，frontmatter 都設了 disable-model-invocation: true：模型不能自己決定「現在該進 emergent-grill 了」「該拆票了」。什麼時候進入下一個流程，永遠是人類的決定。這是 emergent skills「人類主權」設計最先看到的具體表現：流程的節奏屬於人，流程內的執行屬於 agent（完整版在第四章）。

值得注意的是這條線每個流程都可以單獨用。你可以只跑 emergent-grill 不寫 spec；可以拿一份別處來的 spec 直接叫 emergent-spec-review 審；可以手動一張一張叫 emergent-implement 而不用 orchestrator。生產線是預設路徑，不是強制流程——這正是 Matt「不規範流程、規範紀律」取向的延續。

第三章

每個 skill 詳解

這章把第二章那張地圖逐節點展開。每個流程三個欄位：做什麼、怎麼運作、為什麼這樣設計。

流程一・對齊/emergent-grill
做什麼
一場逐題等你回覆的訪談：拷問你的計畫、逼出你沒說出口的假設，每個拍板的決定當場記錄歸檔。整條線上「人完全在迴圈內」的唯一一個流程，不碰任何程式碼。產物：
  • 這場對話紀錄本身：完整的問答與拍板過程，就是下一個流程合成 spec 的素材
  • CONTEXT.md：新拍板的領域詞條
  • draft ADR：重大決定的草稿，落在 docs/adr/draft/
怎麼運作
  1. 先讀你專案的脈絡：開場把共同語言（CONTEXT.md）跟還有效的決策紀錄（ADR）讀進來。你的計畫要是跟某個舊決定衝突，它會當面指出來，不會裝沒看到
  2. 一次只問一題，而且只問值得問的：自己查得到、推得出的不拿來煩你；跟實作時根本遇不到的假想情境，會被它自己的過濾器刷掉；牽涉重大方向的一定問，連「不確定算不算重大」都會問
  3. 問之前，前提先查證：一個問題要站得住，它腳下的前提得先是真的。每個前提都對過來源才拿出來：
    • 跟系統現況有關：翻 codebase 跟文件，不憑印象
    • 本地查不到：搜網路找高可信來源——這是常規動作，不是最後手段
    • 純設計判斷、無從查證：照樣提出，但明講「這是我的低信心判斷」
    提出時每個論點附上出處；沒出處的大聲標低信心，讓你的懷疑集中在該懷疑的地方。「我就是知道」不算證據
  4. 問題長這樣：
    • 把模糊的詞逼清楚：你說「account」，它問你指的是 Customer 還是 User
    • 用具體情境戳邊界：發明一個 edge case，逼你講清楚兩個概念的分界
    • 拿 code 對質：你說系統現在怎麼運作，它會翻 code 查證，不憑印象
  5. 拍板就歸檔：每當你明確定案一個答案，它馬上處理去向：
    • 是領域詞彙：給你看完整詞條，你點頭才寫進 CONTEXT.md
    • 是重大決定：呼叫 /emergent-adr 檢查三個 ADR 形成條件（難以回頭、沒脈絡會令人意外、真實取捨的結果），全數滿足才寫成 draft ADR
    • 都不是：明講「這條不記錄」跟為什麼，絕不沉默略過
  6. 不會自己宣布問完了：想收尾之前得先列出「如果只能再問三題，會問什麼」，一輪一輪列下去，直到真的想不出值得問的問題，或是你手動喊停
為什麼這樣設計
  • 品味榨取器：好設計的判斷力寫不成規則塞給 agent，那是說不出口的手感；但「逐題追問」的流程可以把你腦中的判斷逼出來，變成之後 agent 用得上的白紙黑字
  • 最貴的錯誤攔在最便宜的階段：你以為的「匯出」跟 agent 理解的差三個 edge case，這個差異會安靜穿過 spec、tickets、變成 code，驗收那天才炸
  • 爛問題有專門的剋星：沒價值的問題被「只問值得問的」過濾掉；前提錯誤的問題被「問前查證」擋下——查一次的成本，遠小於一個自信但錯誤的前提被拍板進 spec 的成本
  • 濾網從不放鬆，但也不提早收攤：連收尾前列的候選題都要過同一道過濾，爛題在任何階段都不會被問；但只要濾網後還有值得問的就不停——多跑一輪的成本，遠小於漏一題無聲流進之後的放手執行
跟官方 grill-with-docs 的差異
官方 grill-with-docsemergent-grill
提問節奏一輪攤開全部問題一次一題（取捨：深度換效率）
問題品質事實自己查、決定歸使用者再加問前過濾與前提查證
歸檔把關詞條確定就寫；ADR 口頭問你詞條你確認才寫；ADR 過獨立審查

流程二・規格/emergent-to-spec
做什麼
把剛結束的對話合成一份 spec 文件，發佈後自動審查到收斂。它不訪談、不重新釐清需求：素材就是你們已經討論定案的東西。產物：
  • 一份 spec 文件：發佈在 issue tracker、審查收斂、標好 ready-for-agent，並列明相關的 draft ADR
怎麼運作
  1. 照官方 to-spec 的流程跑：探索 repo、寫 spec、發佈。過程中只跟你確認一件事：這個功能的行為要從什麼層級驗證（例如從 API 層測、還是從畫面測）——官方把這個層級叫 testing seam，指測試伸進系統觀察行為的位置；它會用這個詞問你，你確認的答案會寫進 spec
  2. 寫的時候守一條紅線：只有你們拍板過的才寫成要求；聊過但沒定案的想法、agent 自己的偏好、沒人定的內部結構，一律不寫
  3. 把相關的 ADR 列進 spec：這場對話裡建立或修改過的 draft ADR、以及這份 spec 必須遵守的既有 ADR，都列在 spec 文件裡——下游流程靠這份清單知道該讀哪些、收尾該處理哪些
  4. 發佈後自動送審：每一版 spec 交給 emergent-spec-review 雙軸審查（下一節）
  5. 逐條處置審查發現：
    • 主張成立、已有拍板依據：做最小修復
    • 主張不成立：駁回，記下理由跟查過的證據
    • 只有你能決定：先記進待問清單
  6. 修過就再審：文字動過，前一輪報告作廢、整個審查重跑，直到收斂
  7. 問題攢成一批問你：全部能自己推進的都做完後，一次把待問清單拿回來；你答完，更新 spec、標 ready-for-agent
為什麼這樣設計
  • 必經的交接層：下游實作者看不到你們的對話，只看得到 spec；沒有這個流程，決定散在對話紀錄裡，每個實作者各自腦補一版需求
  • 不准寫沒拍板的：防更隱蔽的災難——spec 把「聊過的探索」寫成約束，實作者被不存在的決定綁死
  • 問題攢成一批：中間不打擾，你不用全程陪跑
跟官方 to-spec 的差異
官方 to-specemergent-to-spec
產物審查沒有專門的審查階段以 emergent-spec-review 自動雙軸審查，並修正到收斂
Spec 能寫什麼模板有「實作決定」一節，agent 認為定案的都能寫多一道限制：對話裡沒真正拍板的東西，不能寫成實作者必須遵守的要求
跟 ADR 的關係寫 spec 時會參考專案裡已有的 ADR還會把這次討論產生的 draft ADR 清單附在 spec 上，後續流程才知道要讀、要處理哪幾份
流程二之內・審查引擎emergent-spec-review
做什麼
對一份凍結的 spec（稱作 Candidate）做雙軸審查。只報問題，不改文件、不寫修法。被 emergent-to-spec 呼叫，也可以單獨拿任何來源的 spec 來審。產物：
  • 兩份 blocker 報告：各自列出「不修就會害實作者做錯」的問題
怎麼運作
  1. 兩個互相隔離的審查者平行開跑：
    • 拿到完整對話的：呼叫端先用 extract-transcript skill 把這個 session 到目前為止的對話紀錄（包含 grill 的完整問答）擷取成檔案交給它。它雙向核對——你拍板的每個決定都寫進 spec 了嗎？spec 的每個要求都真的有人拍板過嗎？
    • 刻意看不到對話的：只憑文件判斷——實作者拿著這份東西，建得出來、驗得出來嗎？
  2. 處置權在呼叫者手上：報告只列問題；修不修、怎麼修，由 emergent-to-spec（或你）決定
為什麼這樣設計
  • 隔離是儀器：看不到對話的審查者判斷不出來的東西，未來的實作者同樣判斷不出來——它的無知精確複製了實作者的處境
  • 審查與修復分離：審查者不寫修法，防它的偏好污染 spec
流程三・拆票/emergent-to-tickets
做什麼
把定稿的 spec（或一個計畫、或這場對話）拆成一批票，發佈到 tracker。產物：
  • 一批 tickets：每張標明要先做完哪些票才能動工，並附回原始 spec 的連結
怎麼運作
  1. 拆票的依據只有你給它的東西：spec、計畫、或這場對話。它不會自己去專案裡翻舊文件來當需求
  2. 照官方 to-tickets 的切法：每張票是一小片能跑的功能：做完就能實際跑起來、驗收得了，而不是「先做完整個資料層」這種要等別人才驗得了的半成品
  3. 票上只寫目標，不寫作法：要做什麼、怎麼算做完；討論過但沒拍板的實作方式不會被寫成規定。所以票看起來很薄——是故意的
  4. 每張票自己講完整：之後做這張票的 agent 是全新開場、看不到其他票，所以每張票都寫清楚：做什麼、怎麼驗收、排在誰後面、完整需求去哪看
為什麼這樣設計
  • 壞一張不拖垮全部：票是失敗的隔離單位——哪張出事就凍哪張（跟被它擋住的），其他照跑
  • 整合問題提早爆：每張做完都真的能跑，接不起來的問題第一張票就會發現，而不是全部做完的最後一天
  • 作法留給實作調整：票只定目標；把作法寫死，等於把沒人拍板的猜測變成規定
跟官方 to-tickets 的差異
官方 to-ticketsemergent-to-tickets
票的內容票上寫：做什麼、被誰擋、怎麼驗收同樣格式，多一道限制：討論過但沒拍板的實作方式，不准寫進票裡
連回 spec不強制每張票必須自足地帶路回 parent spec
流程四・排程/emergent-implement-tickets <tickets-directory>
做什麼
AFK 的一條龍實作調度者：你把一個裝著 tickets 的目錄交給它、回答兩個問題，然後就可以走開；它照依賴順序把票一張一張做完。它自己不寫任何 code，只負責派工、驗收、整合。它不是必經流程，只是建議使用的懶人包：你完全可以自己組織票跟票之間怎麼跑實作、做完自己手動收尾歸檔 draft ADR。產物：
  • 一條整合好的分支：做完的票全部合進來、測試全部通過
  • 一份收工報告：哪些做完了、哪些卡住了、哪些事等你決定、哪些現場留給你看
怎麼運作
  1. 先驗收件：檢查這批票的依賴關係合不合理、是不是每張票做完都能通過全部測試。不合格的票組它不接，會請你手動處理
  2. 開跑前把該問的一次問完：程式碼要不要在獨立的工作目錄跑、做完的東西合到哪條分支；如果工作目錄裡有還沒 commit 的變更（通常是剛 grill 完留下的 CONTEXT.md 跟 draft ADR），也會問你要怎麼處理，需要帶走的就幫你帶到執行用的分支上。答完它就不再出聲，你可以去做別的事
  3. 一次只做一張票，嚴格串行而不平行：從還沒被其他票擋住的裡面挑一張，交給一個全新的 agent 用 emergent-implement 實作
  4. 每張票做完就驗收：測試通過才合進分支，合完才開下一張
  5. 出事有劇本：
    • 一張票失敗：把做到一半的東西留在原地存證，換一個全新的 agent、帶著失敗紀錄重做一次
    • 又失敗：這張票跟等它的票先擱置，其他不相干的照做
    • 撞到只有你能決定的事：標記起來先跳過；等你裁決完，下次再跑它會接手補做
  6. 全部做完最後總驗：整批對照 spec 檢查有沒有漏掉的需求、不同票之間有沒有重複做或叫法不一致；最後呼叫 /emergent-adr 把這一輪的 draft ADR 定案歸檔（見收尾）
為什麼這樣設計
  • 嚴格串行，不平行：平行做票，每張票各自「長」出來的設計會彼此有落差，事後整合的成本未必比平行省下的時間划算。串行讓每張票永遠基於前面已完成、已整合的 codebase 開工——emergent 的基準穩定不偏移，後面的票就能延續前面票長出來的成果繼續長
  • AFK 不等於失控：派工、驗收、出事怎麼辦的規則全部事先寫死；需要人判斷的它不會擅自決定，全部留在報告裡等你
  • 每張票都是全新的 agent：上一張票的思路不會帶進下一張；票跟 repo 本身就足以說明要做什麼
  • 重做是換人、不是續命：失敗後從乾淨狀態重來，比在半成品上硬修更容易做對；失敗的經驗用一份紀錄帶過去就夠
流程五・實作emergent-implement
做什麼
實作單一一張票。由流程四派工呼叫，或由你直接指名使用。啟動條件：一次恰好一張票、票上明確寫出要做什麼與驗收標準；條件不滿足就不會動 code。產物：
  • 做完並通過測試的 code：commit 在當前分支上
  • 一份回報：開頭第一行就講結果——做完了、卡在等你決定、還是失敗了
怎麼運作
  1. 先讀工作方法才動手：emergent-design（哪些事它能自己決定、哪些不行）、官方 codebase-design（怎麼設計好模組）、官方 tdd（先寫測試再寫 code）
  2. 分清楚什麼能動、什麼不能動：票上白紙黑字定好的，照做，不自作聰明改掉；票上沒講的內部細節（module 怎麼切、東西叫什麼名字），它邊做邊決定
  3. 小步推進：每完成一小段就實際執行、測試通過後才做下一段，而不是全部寫完才一次驗證
  4. 遇到票上沒答案、又輪不到它決定的事：那一塊先停下，其他能做的照樣做完、驗完，最後把問題帶回來問你。「這題很難」不算——難題它要自己解；只有「答了等於替你做決定」的才會拿回來問
  5. 做完先自我檢查再交卷：跑全部測試、用官方 code-review 對照團隊標準與原始的票自查一輪，該修的修完才 commit
為什麼這樣設計
  • 這裡就是「emergent」發生的地方：前面的流程只定了「要什麼行為」；「程式長什麼樣」在這裡跟著真實的 code 與測試長出來
  • 「難」跟「不該我決定」是兩回事：難題自己解，防它凡事跑來問你；會替你做主的問題一定回來問，防它越權
跟官方 implement 的差異
官方 implementemergent-implement
開工條件做你指給它的工作，沒有硬性門檻恰好一張已定案的票；範圍或驗收標準不清楚就不動工
撞到沒人決定過的問題沒有明文規則內部作法自己定；會替你對外做主的，凍結那部分、回報等你裁決
工作方法「盡量用 /tdd」emergent-design 與 codebase-design 載不進來就不開工，再配 tdd 紅綠迴圈
收尾/emergent-adr finalize-draft-adrs
做什麼
處理流程一留下來的 draft ADR。實作完成之前它們一直是草稿；現在 code 已經落地，要決定每一份的去留：轉正、還是刪掉。通常由流程四收尾時自動呼叫，你也可以自己跑。
怎麼運作
  1. 先判斷還需不需要留：如果這個決策已經能從 code 跟測試直接看懂，就不需要一份 ADR 再講一次，刪掉
  2. 檢查寫得夠不夠好：內容不合格的先修好
  3. 掃描檢查與既有 active ADR 的決策推翻關係：如果它推翻了某些既有的 active ADR 決策，把推翻關係標記清楚
  4. 轉正：搬進 active/，從此不可修改；之後要改主意，只能寫新的草稿來取代它
為什麼這樣設計
  • 功能做完，每種知識都有了自己的家：行為在 tests、實作在 code、詞彙在 CONTEXT.md、決策的來龍去脈在 active ADR。spec 跟 tickets 的任務到此結束，之後不再維護

地圖上還剩三個不在生產線上的節點：兩個被上面每個流程反覆呼叫的共用 skill，跟一個提供對話證據的工具。

共用・哲學emergent-design
做什麼
整套 skills 共用的工程哲學，第一章講的內容就是它的本文。純參考文件，沒有流程可跑：其他 skill 在開工前把它完整讀進來，用它來做判斷。
怎麼運作
  1. 誰用它：emergent-grill、emergent-to-spec、emergent-to-tickets、emergent-implement，連 emergent-spec-review 派出去的兩個審查者，開工前都要完整載入它
  2. 只認完整本文：描述、摘要、轉述、憑記憶，都不算載入
  3. 載不到就停：整場結束，不產出半份成品
為什麼這樣設計
  • 規則只活在一個地方：哲學改一處，所有 skill 同步生效，不會出現五份各自過期的複本
  • 防漂移：第一章講過，agent 的紀律會隨 context 漂移，「記得的哲學」也一樣會漂。每次都重新載入完整本文，把「用漂移版哲學做判斷」這條路封死
  • 寧可停，不硬跑：載不到就停的反面是「盡力而為」——硬跑的系統看起來還在運作，產出卻已經沒有保證，而且沒人會發現
共用・ADR 機制/emergent-adr <operation>
做什麼
ADR 所有操作的唯一入口。在 emergent skills 裡，ADR 不是一個 markdown 模板，是一套有生命週期、有審查、有推翻關係的系統；誰要動 ADR（寫、審、掃描、轉正）都透過它的操作，不自己動手改檔案。
怎麼運作
  1. 用操作名呼叫：/emergent-adr <操作>；缺了操作名或名字不對，它列出合法清單然後停，不從上下文猜你要幹嘛
  2. 三個資料夾就是三種狀態：
    • draft/：草稿，還沒實作，可以自由修改
    • active/：已實作、還有效，不可修改；要改主意，只能寫新草稿去推翻它
    • archived/：所有決策都被推翻，退場，平常不會被讀到
  3. 開場只讀索引：每份 ADR 有一行「管什麼議題」的描述（只寫議題、不寫結論）；其他 skill 開場只讀這份清單，判斷相關才打開全文
  4. 機械的事交給 script：編號發放、狀態計算、審查報告的驗證，都由 script 處理，不讓 agent 手寫
十一個 operation
九個基礎操作，加上兩個把它們串起來的一條龍。先認識基礎操作：
Operation做什麼
write照格式建立或修改一份草稿的內容；只負責寫，不判斷值不值得寫
quality-review找一個沒看過討論過程的獨立審查者，評這份 ADR 寫得好不好
revise審、修、再審直到過關的迴圈；審查由 quality-review 執行，一次交付最多七輪
scan-supersession掃描一份草稿推翻了哪些還生效的舊決策
promote-draft-to-active把草稿轉正搬進 active/，並標記被推翻的舊決策
check-adr-redundancy查這份 ADR 講的事，是不是 code 跟 tests 已經講清楚了
check-should-write-adr寫入前的守門員：裁定一個決策夠不夠格成為 ADR（emergent-grill 的歸檔 gate 用的就是它）
extract-active-adr-desc列出所有生效 ADR 的一行描述清單，不開全文。emergent-grill 開場就是用它認識既有決策：先讀清單，判斷跟本輪相關才打開該份全文
read-necessity-conditions載入「什麼決策值得寫 ADR」三條件的原文定義。emergent-grill 自審該不該寫 ADR 時、check-should-write-adr 審查時，都會自動呼叫它取得同一份定義

兩個一條龍入口把上面的積木照固定順序串起來：

  • produce（從零寫好一份 draft ADR；人類專屬入口，你說要寫就寫）：write → revise → scan-supersession
  • finalize-draft-adrs（把一批草稿收尾；流程四結尾呼叫的就是它）：對每份草稿跑 check-adr-redundancy → 需要改寫時 write → revise → scan-supersession → promote-draft-to-active
基礎操作全部都能單獨呼叫，不是只能透過一條龍。
為什麼這樣設計
  • 一個入口，規則不散落：每份規格只活在一個檔案裡，改一處、處處生效
  • 狀態就是位置：看檔案在哪個資料夾，就知道它能不能改，不用讀內文
  • 描述索引省 context：幾十份 ADR 的專案，開場成本仍然只是一張小清單
  • script 防手滑：狀態讓人手寫，就會出現第二份會漂移的副本；審查報告讓 agent 手寫，就可能被編出來。機械的事交給機械，才驗得了真假
工具・對話擷取extract-transcript
做什麼
把當前 session 的對話紀錄擷取成一個檔案。它是通用的工具 skill，不屬於 emergent 系列，任何需要對話原文的場合都能呼叫；emergent skills 只是它的使用者之一。
怎麼運作
  1. 工具本身只做一件事：把這個 session 到目前為止的完整對話（包含 grill 的問答與你拍板的每一句）輸出成檔案；session 紀錄檔的位置由另一個工具 skill transcript-path 負責解析
  2. 在這條生產線上目前的使用者：
    • emergent-to-spec：每一輪送審前擷取一次、切到你最新的一句話，交給 emergent-spec-review 裡「拿到完整對話的」審查者當證據
    • /emergent-adr check-should-write-adr：裁定一個決策夠不夠格成為 ADR 時，用它擷取對話證據來核對
為什麼這樣設計
  • 審查者要的是原文，不是轉述：讓 agent 摘要對話，可能漏掉或美化你的決定；擷取原文，審查者對著你真正說過的話核對
  • 每輪重新擷取是呼叫端的紀律：你在審查過程中的回答也是拍板；emergent-to-spec 每輪重擷取，免得審查者把新決定誤判成沒人拍板過
第四章

設計決策解說

前面的章節把每個流程的設計理由就地講完了。還剩三個跨越所有流程的決定，沒有任何一張卡片裝得下，值得單獨講清楚。

一、不複製官方 skill，執行時直接讀原版

emergent-to-spec 跟 emergent-to-tickets 都需要官方 to-spec／to-tickets 的流程。拿到這個流程有兩種做法：把官方內容複製進自己的 skill，或是每次執行時去讀安裝在旁邊的官方原版。這裡選了後者。

  • 複製的問題：複製完成的那一刻起，你手上就是一份不會再更新的副本。官方修了 bug、改了流程，副本毫不知情，也沒有人會提醒你它過期了
  • 現讀原版的好處：官方更新，下次執行直接生效；自己加的規則跟官方的流程分屬兩個檔案，永遠不會混在一起改壞
  • 代價：官方 skill 必須安裝在旁邊；搬家、改名、或用別的方式管理，就會直接停工（好消息：是停，不是亂跑）

二、可以驗證的事，不接受口頭宣稱

為什麼不信 agent 說「做完了」？第一章講過：agent 沒有穩定的紀律自我，偏離的時候還會把偏離講得像判斷。所以整套 skills 凡是能驗證的都直接驗，不聽解釋：

  • 審查報告有固定格式：多寫一個欄位、審到一半收工，整份作廢——沒辦法用漂亮的文字灌水
  • 審查期間文件凍結：被動過一個字，該輪作廢重來——不能一邊審一邊改
  • 沒發現問題也要交代查了什麼：沉默不算通過
  • 「做完了」的標記要對得上 git 紀錄：標記與歷史不符時，以歷史為準

序章那四種失敗模式（偷改 test、做九成宣稱完工、話術遮蓋），全靠「宣稱被當真」才能得逞；在這套機制下它們沒有生存空間。

三、人決定方向，機器負責執行

整套 skills 對「什麼歸你、什麼歸 agent」切得很乾淨：

  • 歸你的：什麼時候進下一個流程（每個流程都要你親自啟動）、所有「別人會依賴」的決定（第一章那條邊界）、draft ADR 最後留不留
  • 歸 agent 的：流程內的執行、排程、審查、驗證

而且兩邊互不越界：emergent-grill 不會替你拍板重大決定，調度者跑起來也不會中途打斷你，該問的攢著一次問。「不越權」跟「不打擾」是同一個設計的兩面。

第五章

限制

以下是這套設計自帶的取捨，不是待修的缺陷：選了確定性，就要付這些成本。用之前該知道。

小事不值得走這條線

修一個 typo 不需要 emergent-grill → spec → 審查 → tickets。這條線是為「一個功能」以上的規模設計的；小改動直接做，或單獨用 emergent-implement。沒有任何機制強迫你走完整條線，但這也表示「這件事值不值得開一條線」的判斷完全留給你：判斷錯了，不是白付流程成本，就是該有的把關一道都沒有。

吃強模型，也吃 token 跟時間

每次都完整載入權威、每輪重跑的雙軸審查、一票一個全新的 sub-agent、一層層的驗證——每一項都在花 token 跟執行時間換確定性；調度的嚴格串行更是明著拿時間換整合品質。而且整套設計預設執行者有前沿模型等級的判斷力（emergent-spec-review 明文指定審查者用 Opus 級模型）。用便宜模型跑，紀律機制還在，但流程內判斷的品質會垮。

CONTEXT.md 與 ADR 需要人在場

詞條寫入的鐵則是「你沒有印象拍板過的意義，絕不能進 CONTEXT.md」——這保護了詞彙表不腐爛，但也表示沉澱的速度被你出席 emergent-grill 訪談的頻率限制。ADR 同理：draft 堆著不收尾，active 就不反映現實。這套系統做到了「文件不會自己爛掉」，但「文件持續長出來」仍然需要你定期回來。
